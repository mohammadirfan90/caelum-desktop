## 2. ⚕ Spot-check readings (CR-002 OI-A, top priority) — new SR-019
- **Change:** every observation carries `measurement_mode` = `continuous` | `spot`, set from the
  device profile. Spot sources: PLX spot-check, BPS, HTS, WSS, glucose and manual entry.
  Rules evaluate spot readings with a confirmation pattern instead of time persistence:
  1. First breaching spot reading → alarm state `CONFIRMING` at the rule's priority: immediate
     prompt to re-measure now, CMO notified, shown as an alarm (never hidden).
  2. A second breaching reading within `confirm_window_s` (draft 300 s) → full alarm; normal
     escalation starts at that moment.
  3. No repeat reading within `recheck_timeout_s` (draft 120 s critical, 600 s warning) → full
     alarm anyway; the system never waits silently.
  4. A non-breaching repeat reading → `CONFIRMING` closes as "not confirmed", logged with both
     values.

  Spot baselines (e.g. weight) use n-of-m: deviation in k of the last n readings (draft 3 of 4).
  Engine support and table-driven tests in M3; all values live in the signed ruleset.
- **Reason:** time persistence can never be met by a single spot reading, so a spot SpO₂ of 80 %
  never alarmed and `baseline.weight` could never fire.
- **Requirements:** new SR-019; SR-003 (persistence applies to continuous readings); F-ALM-01,
  F-ALM-08. **Safety:** H-01 reduced (spot breaches always surface). **Tests:** table-driven tests
  for each branch (1–4) and the n-of-m baseline (M3).
- **Open (proposed by Claude, medical lead to confirm):** a confirmed spot alarm clears on one
  reading that meets the rule's clear threshold; latching rules still need acknowledgement.

## 3. ⚕ Measured fever (CR-002 OI-B)
- **Change:** temperature rules on `body_temp_measured` in spot mode, with per-site thresholds in
  the ruleset. Core-equivalent sites use the `core_temp` thresholds. Peripheral sites get
  separate draft thresholds flagged for the medical lead. An unknown site uses the most
  conservative (lowest) threshold. `core_temp` (estimate) rules stay as they are; both can alarm,
  and supersession applies within the THERMAL category (higher priority supersedes lower across
  `core_temp` and `body_temp_measured` for the same crew member).
- **Site classes (proposed by Claude from the prototype's mapping, medical lead to confirm):**
  core-equivalent = body (general), ear, GI tract, mouth, rectum, tympanum (HTS Temperature Type
  2, 3, 5, 6, 7, 9); peripheral = armpit, finger, toe (1, 4, 8).
- **Peripheral draft thresholds (proposed by Claude as engineering placeholders, not clinical
  values; medical lead to set):** core thresholds minus 0.5 °C, i.e. warning > 37.5, critical
  > 39.0; clears ≤ 37.2 / ≤ 38.5. Being lower, these are also the unknown-site thresholds.
- **Requirements:** SR-006 (supersession group), SR-019, F-ALM-01. **Safety:** H-01 reduced.
  **Tests:** per-site and unknown-site tests; THERMAL supersession across both parameters (M3).

## 4. Identity, licence, version
- **GitHub:** the product owner creates the private repository and supplies the URL. Claude does
  not create it.
- **Bundle identifier:** to be supplied (the decision record gave the template value
  `[org.yourteam.caelum]`). Needed before M0 step 2.
- **Licence:** Apache-2.0 (as NASA Open MCT and cFS). `LICENSE` holds the canonical text from
  apache.org; `NOTICE` holds the project notice and, as they are added, third-party attributions
  (Outfit font OFL-1.1 in M0, LOINC in M1). The cargo-deny licence allow-list must stay compatible
  with Apache-2.0 distribution.
- **Version:** starts at 0.1.0. 1.0.0 = every M-priority feature of the feature lock complete
  and gated.

## 5. Supporting crates (dependency policy)
- A crate not named in the CLAUDE.md stack may be added **without a CR** if it has a permissive
  licence that passes cargo-deny, is actively maintained, does no network access or native
  downloads at build time, and is recorded in `docs/third-party-risk.md`.
- A **CR is required** for any crate that replaces a stack item, or that is used in
  `caelum-alarms`, `caelum-ingest`, `caelum-security`, `caelum-cluster`, crypto code or network
  code.
