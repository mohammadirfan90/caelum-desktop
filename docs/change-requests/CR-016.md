# CR-016: M10 ground integration and medical data system: design decisions and dependencies

- **Status:** approved 2026-10-10 by engineering under the product owner's standing delegation.
  No new feature: records the decisions M10 needed that the documents do not state, the stack
  deviation for CFDP, and the dependencies added to network and ground code (CR-003 §5).
- **Affects:** `caelum-ground`, `caelum-mds`, `plugins/openmct`; F-GND-01..07, F-GND-09,
  F-GND-11 (publish side), F-GND-12..14, F-SYS-08, SR-011, SR-015, SR-016, R-SEC-06,
  R-INT-05..07; `docs/icd/ICD-VEH.md` §4/§5, `docs/icd/ICD-MDS.md`.

## 1. Why
M10 implements the ground and medical-data-system paths. The plan names the crates
(`spacepackets`, `cfdp-rs`, `quick-xml`) but not the packet layouts, the APID plan content,
the CFDP subset, how the OPS field set is enforced, or how the MDS connector routes items. These
are fixed here so that the lead's wiring, the XTCE database and the Open MCT plugin agree.

## 3. CFDP: minimal compliant subset instead of `cfdp-rs` (stack deviation)
`cfdp-rs` 0.3 states that it does not implement suspending transfers or transmission-opportunity
handling, which are exactly what F-GND-06 needs (transactions only during contact windows,
suspended at LOS, resumed at AOS); its handlers keep their state private, so the missing
procedures cannot be built on top; and it pins `spacepackets` 0.16, which would put two versions
of the packet crate in the build. Decision: `caelum-ground::cfdp` implements the procedures,
sans-I/O, using the `spacepackets` PDU types for every PDU on the wire:
- class 1 (unacknowledged) **with transaction closure** (the receiver always sends Finished; the
  sender waits for it on a check timer), so the sender learns the outcome and the queue can start a
  new transaction after a loss; class 1 is therefore at-least-once, and the ground de-duplicates
  by file name and digest;
- class 2 (acknowledged): Metadata, File Data, EOF, ACK(EOF), NAK with segment requests (and the
  metadata request `(0, 0)`), Finished, ACK(Finished); positive-ACK and NAK timers and limits;
- Suspend / Resume for all transactions at contact-window boundaries; timers run on active time
  only, so a 30-day LOS never exhausts a limit;
- normal file size (< 4 GiB), PDU CRC on, modular checksum, no segment metadata, no filestore
  requests, no Keep Alive / Prompt / inactivity procedures;
- transaction state is serialisable; outgoing file content is re-attached from the attachment store
  after a restart and checked against its digest;
- incoming PDUs are decoded inside `catch_unwind`: `spacepackets` decoders index into buffers, and a
  malformed PDU must be rejected, not crash the core. Fuzzing the decoders is an open item (§8).
Interoperability with another CFDP implementation (e.g. the Python `cfdppy` used by `cfdp-rs`'s
own interop example, or the vehicle's CFDP entity) is verified in the CI job of
`docs/integration/M10.md` §6.

## 4. Packets, APIDs and XTCE
- Every CAELUM packet is telemetry (type bit 0), unsegmented, with a 7-octet secondary header:
  CUC P-field `0x1E` (CCSDS epoch 1958 TAI, 4 coarse + 2 fine octets). `TmPacket::build` is the
  only constructor and takes no packet type, so a telecommand cannot be built (SR-011; tested).
- APID plan (signed `ground` configuration bundle, kind `ground`, with the path B endpoint and the
  CFDP entity IDs): `ops_instance_status`, `ops_crew_status`, `ops_alarm`, `medical_summary`,
  `cfdp`. All distinct, 0..=2046. No defaults. Contact windows: signed bundle kind
  `contact-schedule`.
- Per-APID 14-bit sequence counts, persisted with the queue state.
- XTCE 1.2: an **OPS** database for mission control (headers and OPS containers only; it names no
  physiological parameter) and a **full** database for the flight-surgeon / BME ground system with
  one derived container per downlinked catalog parameter (restricted on the parameter index).
  Parameters whose states are pending (`spe_state`) are never downlinked and are not in the MDB.

## 5. OPS channel enforced by type (R-SEC-06, docs/06 §3a)
`OpsRecord` is one of `Alarm` (crew UUID, priority, category, state, escalation stage, creation
time, record time), `CrewStatus` (crew UUID and the highest active alarm's priority, category and
state, or none) or `InstanceStatus` (instance health, MDS link state). All fields are closed
enumerations, a UUID or TAI times; encodings have fixed lengths (26, 19, 2 octets). The alarm-core
names are mapped strictly; an unknown name is refused, never defaulted. The OPS state list adds
`acknowledged` and `ended` to the engine's states, because ICD-VEH §6 requires a packet on every
state change. "Technical health" (docs/04 §3, ICD-VEH §5) is the `InstanceStatus` record; no
technical parameter value goes on OPS. The downlink queue refuses any other payload on OPS.

## 6. Medical data system connector
- Routing is a pure function (F-GND-13, SR-015): alarm events and ground escalations always take
  path B, whatever the MDS state; the medical record goes on path A when the MDS accepts it, else
  per mission policy: hold until reconnect, or A' (direct CFDP) **and** hold, so the onboard record
  is still completed after reconnect (the ground de-duplicates by client id). Raw waveforms without
  an event link or ground request are not sent (F-GND-14).
- Client ids are SHA-256-derived UUIDs (version 8) over a CAELUM namespace, the resource kind and
  the local record id: retries and restarts produce the same id, so conditional create is
  idempotent. (UUID v5 would need SHA-1, which the workspace does not carry.)
- 4xx responses (except 408 and 429) are held for review, never retried; 5xx, timeouts and link
  failures are retried with deterministic exponential back-off.
- Health is never `connected` before a successful exchange; a technical alarm is raised once when
  the MDS is unreachable longer than the configured limit and cleared on the next exchange that
  proves contact.
- **No HTTP client crate is added in M10.** `FhirTransport` is a trait with an in-memory fake FHIR
  server for tests. The production transport (HTTPS, TLS 1.3, mutual certificates, ICD-MDS §3) is
  network code and needs its own decision: proposed `hyper` 1 client (`hyper-util`, already in the
  lockfile through Tauri) over `rustls` (stack) with `tokio`, wrapped behind `FhirTransport`.
  It is a lead integration item (`docs/integration/M10.md` §2) and is gated by the HAPI FHIR CI job.

## 7. Store-and-forward queue
- Items are allow-list checked, signed (Ed25519, domain tag `CAELUM-DOWNLINK-1`, by the instance
  key) and persisted before they are accepted; a store failure refuses the item.
- On reload an item whose signature does not verify is quarantined (never sent) and reported.
- Priorities CRITICAL → ROUTINE → RESEARCH, FIFO within; packets are removed only after the link
  confirms them; files only when their CFDP transaction completes; a cancelled transaction is
  restarted.
- The MEDICAL allow-list is the catalog's (parameters allowed on MEDICAL with defined states); a
  mission may narrow it, never widen it. RESEARCH carries only de-identified exports.
- Path B uses its own OPS-only queue instance (own store rows, own sequence counts), always "in
  contact" with the onboard endpoint, so OPS records survive an endpoint outage or a restart.

- CFDP interoperability test against an independent implementation; fuzzing of the PDU decoders.
- ICD-VEH OI-1 (entry into cFS) still open: path B emits to the configured UDP endpoint.

## 9. HTTPS transport (amends §2, §6 and §8)
- **Status:** approved 2026-10-10 by engineering under the product owner's standing delegation.
  Network and crypto code (CR-003 §5), so recorded here. Implements F-GND-12 and R-INT-05 over
  ICD-MDS §3 (TLS 1.3, mutual certificates).
- **Decision:** `caelum_mds::https::HttpsTransport` implements `FhirTransport` with `ureq` 3
  (blocking HTTP/1.1, `default-features = false`, feature `rustls-no-provider`) over `rustls`
  0.23 (stack) with the `ring` crypto provider only (`default-features = false`, `ring`, `std`).
  This replaces the §6 proposal of `hyper` 1 + `hyper-util` + `tokio`.
- **Why `ureq` and not `hyper`:** `FhirTransport` is a blocking trait and the connector is
  sans-I/O, so an async client would need a runtime handle and `block_on` inside the trait;
  `hyper` 1 needs `hyper-util`, a connector and `tokio-rustls` on top to do TLS, several times
  the dependency surface for the same two requests. `ureq` 3 accepts a caller-supplied rustls
  `CryptoProvider`, a specific root store and a client certificate, which is all mutual TLS
  needs, and can be configured with no proxy, no redirects, HTTPS only, no compression and a
  bounded body. `ring` instead of `aws-lc-rs` keeps the build free of cmake / NASM and of
  aws-lc's large generated C sources; it needs only the C compiler the workspace already uses
  (SQLCipher). Nothing is downloaded at build time (CLAUDE.md rule 8).
- **TLS 1.3 only:** the provider handed to the client keeps only the TLS 1.3 cipher suites, so
  a TLS 1.2-only server is refused (tested). Trust is the mission CA bundle from signed
  configuration only (no `webpki-roots`, no platform verifier, no option to disable
  verification); server name verification on; the client certificate and key are mandatory.
  The complete rustls client configuration is built once in `HttpsTransport::new`, so a bad CA
  bundle, a missing key or a key that does not match the certificate is a configuration error
  before any connection, never a failure inside a request.
- **Behaviour:** conditional create `POST [base]/<type>` with
  `If-None-Exist: identifier=urn:caelum:client-id|<id>` and `Prefer: return=representation`;
  201 → created, 200 → existing; the logical id from the returned resource, else `Location`.
  Search `GET [base]/<type>?_lastUpdated=ge<instant>&_sort=_lastUpdated&_count=<n>`, following
  bundle `next` links up to `SEARCH_PAGE_BUDGET` (8) pages, and only links under the configured
  base URL. Errors are classified per ICD-MDS §9 (connect / TLS → `Unreachable`, timeout →
  `Timeout`, 4xx with `OperationOutcome` diagnostics → `Http4xx`, 5xx → `Http5xx`, anything
  else unexpected → `Protocol`). A request whose resource type is malformed or does not match
  the resource is refused locally as a 400 whose text says "not sent" (held for review, never
  retried). No update, delete or operation call exists (ICD-MDS §7).
- **Closes** the §8 open items "production FHIR transport" and "FHIR paging with `next` links"
  in the library; the HAPI FHIR CI job stays open. Integration, register rows and the licence
  note (ISC): `docs/integration/M10-https.md`.

## 10. Core wiring of the medical data system link (lead, 2026-10-10)
- The connector runs in its own service on its **own connection** to the encrypted database
  (busy timeout 5 s), outside the station lock: network waits never delay alarms. Read-back
  observations are handed to the station, stored as `imported` with quality `degraded` (FHIR
  carries no signal quality; none is assumed) and evaluated like direct data (SR-016).
- Configuration: signed bundle kind `mds` (`[mds]` version, base_url, ca_pem, timeout_ms,
  policy, poll_interval_s, page_size, max_sends_per_tick, summary_window_s, outage_alarm_after_s,
  alarm_backoff_s, routine_backoff_s; all required). Applied by an administrator after
  re-authentication, audited.
- Client identity: certificate and key PEM set by an administrator (re-authentication, audited
  with the certificate digest only) and kept in the encrypted database rather than a separate
  keystore entry, so it follows the records' protection and backup. Decided by engineering under
  the standing delegation.
- Summary-first (F-GND-14): per crew member and parameter, the median of each closed window is
  sent as an `Observation` with an effective period; simulated and unusable readings never are.
- Outage: `technical.mds_unreachable` is raised and cleared from the connector's health signal.
  Tables: migration V7 replaces the unused V1 `mds_outbox` / `mds_inbox`.
