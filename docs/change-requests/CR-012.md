# CR-012: M6 prerequisites: crew roster, user administration, read commands and live events

- **Status:** approved 2026-10-10 by engineering under the product owner's standing delegation.
  No new feature: schedules parts of locked features that no milestone names, and defines the
  commands and events the M6 screens need.
- **Affects:** `caelum-alarms::signing` (config bundles), `caelum-core`, `src-tauri`, `ui`,
  `tools/ruleset-signer`, `caelum-test-equipment`, `docs/ROLE_MATRIX.md` §3; F-SYS-07, F-SYS-01,
  F-ACQ-01, F-ACQ-09, F-ACQ-10, F-ALM-08, F-ALM-09, CR-007 §4.

## 1. Why
`docs/10_BUILD_PLAN.md` gives F-SYS-07 (configuration as signed files) and the user administration
of CR-007 §4 no milestone. The M6 gate needs both: a crew member with an account, and a device
assigned to that crew member. Without them only the first administrator can sign in, and no
device can be assigned. The rest of F-SYS-07 (channels and APIDs) stays with M10, which uses it.
Devices are registered by pairing (F-ACQ-09), not by configuration.

## 2. Crew roster (F-SYS-07, crew part)
- A signed TOML bundle (`crew.toml` with `crew.sig.toml`) using the same envelope, keys and trust
  policy as the ruleset (CR-009 §2). The signed message is
  `"CAELUM-CONFIG-1" ‖ kind ‖ 0x00 ‖ sha256 ‖ version`, so a ruleset signature can never pass as a
  configuration signature or the reverse. An author signature is required; release builds accept
  flight keys only. Signed with `caelum-ruleset-signer sign-config`.
- Content: `[roster] version, mission`; `[[crew]] id (UUID), name, position`. Unknown fields are
  refused.
- Applied by an administrator after re-authentication (`config_apply_crew`, ROLE_MATRIX §4). The
  bundle is verified, stored (`config_bundle`, kind `crew`) and audited (`config.apply`, version
  and digest). Crew members are upserted by ID. Members missing from a new roster become inactive
  and are never deleted, because their records keep their owner. A roster whose version equals
  the one in force but whose content differs is refused.

## 3. User administration (CR-007 §4)
- `user_list`: Administrator, CMO, Flight Surgeon and BME see all accounts (ROLE_MATRIX §2, "Users
  and roles"); the Astronaut and MCC see only themselves.
- `user_create`: Administrator after re-authentication. Sets the role, the crew member (required
  for an astronaut, who must be an active roster member) and an initial secret under the CR-007
  policy.
- `user_disable`: Administrator after re-authentication. An administrator cannot disable their own
  account; because the caller is always an active administrator, the last active administrator
  can never be disabled.
- Both are audited (`user.create`, `user.disable`, category security).

## 4. M6 commands and live events
| Command | Roles | Returns |
|---|---|---|
| `crew_list` | Astronaut (self); CMO, Flight Surgeon, BME, Administrator (all) | Roster: ID, name, position, active. No health data |
| `vitals_latest` | Astronaut (own); CMO, Flight Surgeon, BME (all) | Newest value per parameter with unit, source device, measured time, quality and status (live, stale or signal unusable). A parameter never reported is absent (shown as NO DATA) |
| `vitals_trend` | as `vitals_latest` | One parameter over a window of up to 24 h, plus the personal baseline if one exists |
| `waveform_recent` | as `vitals_latest` | Waveform chunks of one signal over the last 30 s at most |
| `alarm_list` | Astronaut (own); CMO, Flight Surgeon, BME (all); MCC (all, OPS fields only) | Active alarms and those ended in the last 24 h |
| `alarm_detail` | Astronaut (own); CMO, Flight Surgeon, BME (all) | The why, trigger value, rule and ruleset version, escalation timeline (notifications) and the actions taken |
| `alarm_report` | CMO, Flight Surgeon, BME | F-ALM-09 history, statistics and fatigue indicators (§5) |
| `device_list` | Astronaut (own devices); CMO, Flight Surgeon, BME, Administrator (all) | Registry with link state, battery, clock offset and dropped readings (F-ACQ-10) |
| `device_scan`, `device_pair` | CMO, BME, Administrator | Nearby devices with supported profiles, and pairing (F-ACQ-01) |
| `device_assign`, `device_unassign` | CMO, BME, Administrator, after re-authentication (ROLE_MATRIX §4) | Audited |

Events `observationsChanged { crewId }` and `devicesChanged` carry no values. The UI then calls the
authorised commands above, so physiology leaves the core only through a role-checked command
(CLAUDE.md rule 6). This is the same rule as the alarm bus.

## 5. Alarm-fatigue report (F-ALM-09)
Over a chosen window, per rule and priority:
- the number of alarms;
- alarms per crew member per day;
- the median time to acknowledge;
- the share acknowledged before the CMO stage;
- the share silenced;
- the share that ended by themselves within 60 s (a nuisance indicator);
- rules raised 3 or more times within one hour for the same crew member (repeat indicator).

These are engineering indicators for review, not clinical judgements. ⚕ The medical lead reviews
the indicator set.

## 6. Baselines (F-ALM-08)
The engine's baseline rules were delivered and tested in M3, but nothing estimates baselines yet.
The heart-rate and SpO₂ baselines are "at rest", which needs activity context (F-SIG-07, M7), and
unknown context is never defaulted (SR-018). Baseline estimation (median and MAD over a window,
stored in `baseline` with its method version) is therefore scheduled with M7. Until then no
baseline exists: the Body trend says so, and no baseline notice can fire. No baseline is ever
made up.

## 7. ECG strip
The strip shows stored waveform chunks. ECG sources (GHS ECG, the sensor shirt) arrive in M7; until
then the strip shows NO DATA.

## 8. Test equipment for the M6 end-to-end gate
Only in `test-equipment` builds, which the release guard keeps out of releases (CLAUDE.md rule 3):
- an emulated pulse oximeter that appears in `device_scan`, with readings from a scenario file
  that the end-to-end test provides (`CAELUM_TE_SCENARIO`). The emulator never invents a value;
- fault injection `audit-tamper` (`CAELUM_TE_FAULT`), which changes one stored audit entry at start
  so the Audit screen must show the chain as broken.
