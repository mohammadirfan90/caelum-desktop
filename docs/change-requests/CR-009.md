## 2. Signing (SR-009)
- The ruleset is `ruleset.toml`; its signatures are in `ruleset.sig.toml`: the SHA-256 of the exact
  ruleset bytes, the ruleset version, and one or more signatures `{ role, key_id, signature }` over
  `"CAELUM-RULESET-1" ‖ sha256 ‖ version`.
- Roles: `author` (engineering) and `medical_approver`.
- **Development builds** (`debug_assertions`) accept development keys and then show the
  "DEVELOPMENT RULESET" banner. **Release builds** accept only flight keys, and require a valid
  `medical_approver` signature by a flight key.
- Trusted public keys are compiled in (`crates/caelum-alarms/keys/`). No flight key exists yet:
  until a licensed clinician advisor countersigns (CR-003), release builds load no ruleset and
  start in the safe state (technical alarm "no verified ruleset"), which is exactly SR-009.
- The development private key is kept outside the repository (`tools/ruleset-signer keygen`);
  only its public key is committed. A development key can never be trusted by a release build.
- Any failure (missing file, digest mismatch, unknown key, bad signature, parse error, version
  mismatch) rejects the ruleset; the engine keeps the last verified one or, with none, runs no
  physiological rules and raises the technical alarm.

## 3. ⚕ Values the ruleset needs that docs/06 does not state (DRAFT, medical lead and BME)
- `asystole.critical` gate "good ECG SQI": `sqi_ecg ≥ 0.7` (engineering placeholder).
- Spot confirmation per rule from the docs/06 §3 values by priority: `confirm_window_s` 300;
  `recheck_timeout_s` 120 for critical and 600 for warning rules. Every vital-sign threshold rule
  carries them, because any vital sign can arrive as a spot reading (spot devices, manual entry).
- A spot reading on a rule without spot settings (derived and environment values, which arrive
  continuously) raises the full alarm at once: never ignored (SR-019), never delayed.
