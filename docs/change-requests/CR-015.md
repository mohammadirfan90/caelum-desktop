# CR-015: M9 vehicle bridge decisions (MID table, SPE states, time correlation, network code)

- **Status:** approved 2026-10-10 by engineering under the product owner's standing delegation.
  No new feature: decides the open points that M9 (F-ENV-01..03, F-GND-11 subscribe side,
  R-INT-04, F-ACQ-11) needs before the vehicle owner supplies the mission database.
- **Affects:** `caelum-vehicle`, `caelum-test-equipment` (`cfs`), `caelum-domain` (catalog entry
  `spe_state`, applied at integration), `docs/icd/ICD-VEH.md` (v0.2), config bundle kind
  `vehicle`; ICD-VEH OI-2, OI-5, OI-6, OI-7.

## 1. Why
ICD-VEH v0.1 left the inbound MIDs, layouts and `spe_state` values to the vehicle owner. M9 must
build and test the bridge now. This CR fixes the parts CAELUM owns (vocabulary, validation,
time handling, transport limits) and makes everything vehicle-specific configuration, so the
real mission database drops in without code changes.

## 2. Transport: receive only
- Inbound is UDP: one CCSDS packet per datagram (`ccsds`) or SBN UDP application messages
  (`sbn`). The receiver binds, receives and decodes; it never connects, sends or writes
  (SR-011, CLAUDE.md rule 5).
- A full SBN peer exchanges subscriptions and heartbeats, which are outbound traffic. CAELUM
  does not do this. The vehicle forwards the configured MIDs statically (ICD-VEH OI-5). SBN
  control messages that arrive are ignored and counted.
- Datagrams are accepted only from `link.allowed_sources` (required, non-empty) and, for SBN,
  optionally only from `link.sbn_peers`.

## 3. MID table (configuration bundle kind `vehicle`)
- A signed TOML bundle with the CR-009/CR-012 envelope (`"CAELUM-CONFIG-1" ‖ "vehicle" ‖ …`),
  applied like the crew roster. `caelum-vehicle::VehicleConfig::from_toml` parses the verified
  bytes. Unknown keys are refused. Format: `docs/integration/M9.md` §3; example:
  `crates/caelum-vehicle/tests/fixtures/reference.toml` (a test fixture, not flight data).
- Validation at load, all-or-nothing: telemetry MIDs only (type bit clear, secondary header bit
  set, version bits zero), no duplicate MIDs, parameters allowed only in their message kind,
  units required and convertible to the catalog unit, state names from §4, integer flags with
  masks that fit, crew mapping present when a message names a crew field, at most one time
  message.
- Calibration `raw × scale + bias` with `scale` and `bias` optional (identity when omitted).
  This is the absence of a calibration, not a data value.

## 4. `spe_state` values (ICD-VEH OI-2), ⚕ DRAFT
`none`, `watch`, `warning`, `in_progress`, `all_clear` (definitions in
`caelum-vehicle::spe`). The vehicle's integer codes are mapped in the MID table. Unmapped codes
are rejected. On integration, the catalog entry changes from `EnumPending` to
`ValueType::Enum(&SPE_STATES)` (same five names). Pending review by the vehicle owner and the
medical lead. No alarm rule uses `spe_state` yet, so `RULESET_VERSION` is unchanged.

## 5. Quality of vehicle values
- GOOD when the message carries a validity bit for the value and it is set.
- A cleared validity bit drops the value (`sensor_invalid`). The value is never stored as
  POOR and never substituted.
- DEGRADED ("usable with reduced confidence") when the message has no validity bit for the
  value. CAELUM then has no positive confirmation, and claiming GOOD would overstate it.
  Environment rules still evaluate DEGRADED values (SR-005 pauses only POOR and UNUSABLE).

## 6. Time correlation (F-ACQ-11, docs/05 §4)
- Vehicle epoch and scale (TAI or UTC) come from the MID table. MET comes from the signed
  mission epoch, which the caller passes in. UTC-scale times use the signed leap-second table.
- Vehicle time is used only while the vehicle reports its clock set (time message, not older
  than `clock_state_max_age_s`). Otherwise the reading gets the receipt time, marked
  `receipt_unsynchronised`. A vehicle time more than 1 s after receipt is a clock fault and is
  dropped.

## 7. Dependencies (CR-003 §5: network code)
- `tokio` (stack item) with the `net` feature, for the UDP socket. Already in `Cargo.lock`:
  `mio` and `socket2` arrive through the existing `tokio`, so no new crate enters the build.
- `toml` 1 (already used for the ruleset and crew roster) parses the MID table.
- `spacepackets` (stack) is not used. The inbound CCSDS and cFS headers are parsed by hand in
  about 100 lines, fully tested and property-tested against arbitrary bytes. This keeps the
  receive path free of a packet *builder*, so the crate holds no code that can form a packet.
  `caelum-ground` uses `spacepackets` for the outbound path in M10.
- Rows for `docs/third-party-risk.md` are proposed in `docs/integration/M9.md` §6.
