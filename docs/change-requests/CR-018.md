# CR-018: M12 model runtime: `ort` with `load-dynamic`, package format, signatures, time limits

- **Status:** approved 2026-10-10 by engineering under the product owner's standing delegation.
  No new feature: fixes how F-ML-01..04 are built (docs/08), and records the crate decision that
  CLAUDE.md (CR-003 §5) requires for crates used by ML code.
- **Affects:** `crates/caelum-ml` (new code), `Cargo.lock`; integration in `caelum-core`,
  `src-tauri`, `ui`, the tool cache and `docs/third-party-risk.md` (by the lead,
  `docs/integration/M12.md`); F-ML-01, F-ML-02, F-ML-03, F-ML-04, SR-002, SR-005, H-09.

## 1. Why
docs/08 fixes the rules (advisory only, ONNX via `ort` with `load-dynamic`, pinned and
checksummed runtime, hash-pinned signed packages, per-inference time limit, validation status in
the UI, explanations). It does not fix the package format, the signature kind, the time limits, how
model outputs may reach the rule engine, or what happens when the runtime is absent. This CR does.

## 2. `ort` with `load-dynamic`
- `ort = "=2.0.0-rc.13"` (exact pin: a release candidate, like `tauri-specta`), **default features
  off** (no `download-binaries`, `copy-dylibs`, `tls-native`, `ndarray`), features
  `std`, `load-dynamic`, `api-22`. With `load-dynamic` the build script of `ort-sys` neither
  downloads nor links anything (`disable-linking`); the build stays offline (R-OPS-03).
- Behind the `caelum-ml` Cargo feature **`onnx`**, off by default, so default builds and CI need no
  ONNX Runtime binary. A build without the feature uses `NoRuntime`: every model is UNAVAILABLE.
- The ONNX Runtime library path and its SHA-256 come from configuration (`OrtConfig`). Before
  loading, the file's SHA-256 must equal the pinned value of the tool-cache binary
  (`docs/OFFLINE_BUILD.md` §1); `ort` additionally refuses a library older than its API floor.
  Path not configured, file absent, checksum or version mismatch: every model is **UNAVAILABLE**
  with the reason; there is no fallback and no guessed output. The library is loaded once per
  process; CPU only (no execution providers), `intra_threads` fixed by configuration (≥ 1),
  `inter_threads` = 1.
- New transitive crates under the feature: `ort-sys` (MIT/Apache-2.0), `libloading` 0.9 (**ISC**:
  not in the `deny.toml` allow-list; must be allowed by the lead before `onnx` is enabled in a
  shipped build), `ndarray`, `matrixmultiply`, `rawpointer` (MIT/Apache-2.0, lockfile only: not
  compiled with the chosen features).
- Risks (for `docs/third-party-risk.md`): release candidate API drift (exact pin, thin wrapper in
  `caelum_ml::onnx`, the only file that names `ort`); native library loaded at run time
  (checksum before load; `unsafe` stays inside `ort`); ONNX Runtime bugs or slow kernels (hard
  time limit, §4; outputs range-checked, §5).

## 3. Package format and signature
- A package is a directory: `manifest.toml`, `manifest.sig.toml`, and the ONNX file named in the
  manifest (plain file name only).
- `manifest.toml` (unknown fields refused, every field required unless stated):
  `[model] id, name, version, file, sha256`; `[validation] status (VALIDATED | NOT_VALIDATED |
  RESEARCH), gate, evidence (required when VALIDATED)`; `[card] intended_use, training_data,
  evaluation, limitations, approver` (non-empty); `[runtime] time_limit_ms, input_name,
  output_name`; `[[feature]] name, parameter, aggregate (mean | median | min | max | std | last |
  rmssd | series), window_s, min_samples, max_gap_s, length (series only), reference`;
  `[[output]] name, label, index, min, max, parameter (optional), notice (optional: op, threshold,
  title, action)`; `[explanation] top_k`.
- Signature: the configuration-bundle envelope of CR-012 §2 (`caelum_alarms::signing::
  sign_config` / `verify_config`) with **kind `model`** over the exact manifest bytes; the
  manifest pins the model by SHA-256, so the signature covers the model. A ruleset, crew or other
  configuration signature never verifies as a model signature. Author signature required; release
  builds accept flight keys only. The envelope's version must equal `model.version`.
- Release builds refuse `RESEARCH` packages, and a `VALIDATED` package needs, in addition, a
  `medical_approver` signature by a flight key. Development builds accept development keys and the
  UI shows the package as development-signed.
- Any failure (signature, kind, digest, manifest, model hash, size > 256 MiB) rejects the package.
  `VerifiedPackage` can only be built by verification, and runtimes and the registry accept only
  it, so an unverified model is never loaded.

## 4. Time limits
- `time_limit_ms` per package, 1..=1000 ms. Each inference (and each explanation repeat) runs on a
  worker thread; when the limit expires the caller gets `TimedOut` and no output.
- At most one inference per model is in flight: until a timed-out worker returns, further
  requests get `Busy` (no pile-up). A panicking runtime yields `WorkerLost`. None of these yield a
  value.

## 5. Outputs, explanations and SR-002
- Features: missing data, a gap longer than `max_gap_s` (also at either end of the window), too
  few samples, POOR/UNUSABLE quality (SR-005, treated as gaps) or a value not representable as f32
  means **no output**. Nothing is imputed or padded. `reference` (training-set median from the
  model card) is used only for explanations.
- Every output must be finite and inside `[min, max]`, else the whole inference is rejected.
- F-ML-04: explanations by occlusion over the runtime (each feature set to its reference; the
  change of each output is its contribution), top `top_k` per output. No explanation, no output.
- SR-002 by construction: `AdvisoryResult` and `AdvisoryNotice` are display types; a notice's
  level is `AdvisoryLevel::Observe`, a single-variant enum, and nothing converts them into an
  alarm, a priority above observe, an acknowledgement or a suppression. The only path into the
  rule engine is `ObserveOnlyInput::apply`, for the model output parameters `af_probability` and
  `bp_trend_systolic` only, and only if, in the engine's own ruleset, every rule on the parameter
  is an observe-level threshold rule without at-rest context, its groups hold no rule on another
  parameter, and the parameter gates no absence rule, is no at-rest context and no baseline
  parameter. Model M2 (AF) therefore stays observe level (`af.observe`) until VALIDATED, and
  promoting it needs a CR, a ruleset change and a change of this gate (docs/08 §1).
- Validation status shown in the UI: `VALIDATED`; `INVESTIGATIONAL` (NOT_VALIDATED, or RESEARCH in
  development builds); `DISABLED`; `UNAVAILABLE` (no runtime). docs/08 §1 lists the first three;
  UNAVAILABLE is added because a missing runtime must be visible, not silent.

## 6. Verification
`cargo nextest run -p caelum-ml`: package verification (tampered model, tampered manifest, bad
signature, untrusted key, wrong kind, version mismatch, missing and unknown fields, inconsistent
fields, release policy), registry and status, feature builders with gaps, time limit and busy,
implausible outputs, explanations, and the SR-002 adversarial test (NaN, ±inf, 1e30, negative,
out of range, timeouts, panics, empty and oversized outputs, forged results, property test over
arbitrary values): alarm decisions are identical with and without model outputs, except the
observe-level `af.observe`. `cargo check -p caelum-ml --features onnx` compiles the backend.
No trained model and no validation result is created by this CR.
