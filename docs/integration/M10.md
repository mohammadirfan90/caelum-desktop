# M10 integration: what the lead wires

The M10 libraries (`caelum-ground`, `caelum-mds`, `plugins/openmct`) are complete and tested in
isolation (CR-016). This page lists what has to be wired into `caelum-store`, `caelum-core`,
`src-tauri`, the UI, CI and the registers before the M10 gate can be run.

## 1. Storage (proposed migration `V6__ground_and_mds.sql`)
The V1 tables `downlink_item`, `uplink_item`, `mds_outbox` and `mds_inbox` predate the M10 design
and are not used by any code yet. Proposed: replace them.

```sql
-- Store-and-forward queues (caelum_ground::queue::QueueStore). `path` separates the ground
-- downlink queue from the OPS-only path B queue; each has its own ids and link state.
DROP TABLE downlink_item;
CREATE TABLE downlink_item (
    path            TEXT NOT NULL CHECK (path IN ('ground', 'path_b')),
    id              INTEGER NOT NULL CHECK (id > 0),       -- SignedItem.id
    channel         TEXT NOT NULL CHECK (channel IN ('OPS', 'MEDICAL', 'RESEARCH')),
    priority        TEXT NOT NULL CHECK (priority IN ('CRITICAL', 'ROUTINE', 'RESEARCH')),
    item            TEXT NOT NULL CHECK (json_valid(item)), -- SignedItem JSON incl. signature
    created_at_tai  INTEGER NOT NULL,
    PRIMARY KEY (path, id)
) STRICT;
CREATE TABLE downlink_link_state (
    path            TEXT PRIMARY KEY CHECK (path IN ('ground', 'path_b')),
    state           TEXT NOT NULL CHECK (json_valid(state)) -- seq counts, CFDP snapshot, transfers
) STRICT;

-- Uplink ledger (caelum_ground::uplink::UplinkLedger) plus the audit trail of every attempt.
DROP TABLE uplink_item;
CREATE TABLE uplink_item (
    id              TEXT PRIMARY KEY,
    kind            TEXT NOT NULL,          -- ruleset | protocols | model | config:<kind>
    version         TEXT NOT NULL,
    sha256          TEXT NOT NULL,
    outcome         TEXT NOT NULL CHECK (outcome IN ('applied', 'duplicate', 'refused', 'rolled_back')),
    reason          TEXT,
    at_tai          INTEGER NOT NULL
) STRICT;

-- MDS connector (caelum_mds::store::{OutboxStore, InboxStore}).
DROP TABLE mds_outbox;
CREATE TABLE mds_outbox (
    client_id       TEXT PRIMARY KEY,       -- urn:caelum:client-id
    kind            TEXT NOT NULL CHECK (kind IN ('Observation', 'DiagnosticReport', 'Device')),
    priority        TEXT NOT NULL CHECK (priority IN ('Alarm', 'Routine')),
    resource_json   TEXT NOT NULL CHECK (json_valid(resource_json)),
    created_at_tai  INTEGER NOT NULL,
    state           TEXT NOT NULL CHECK (state IN ('Pending', 'InFlight', 'Acknowledged', 'HeldForReview')),
    server_id       TEXT,
    state_at_tai    INTEGER,
    held_status     INTEGER,
    held_reason     TEXT,
    attempts        INTEGER NOT NULL DEFAULT 0 CHECK (attempts >= 0),
    next_attempt_at_tai INTEGER NOT NULL,
    last_error      TEXT,
    CHECK ((state = 'Acknowledged') = (server_id IS NOT NULL)),
    CHECK ((state = 'HeldForReview') = (held_status IS NOT NULL))
) STRICT;
CREATE INDEX mds_outbox_due ON mds_outbox (state, priority, next_attempt_at_tai, created_at_tai);
DROP TABLE mds_inbox;
CREATE TABLE mds_inbox_state (
    id              INTEGER PRIMARY KEY CHECK (id = 1),
    high_water      TEXT                    -- meta.lastUpdated as received
) STRICT;
CREATE TABLE mds_inbox_seen (
    source_id       TEXT PRIMARY KEY,       -- SR-016 de-duplication key
    version         TEXT NOT NULL,
    seen_at_tai     INTEGER NOT NULL
) STRICT;
```
`docs/05_DATA_MODEL.md` §2 must be updated with these tables (the schema test compares them).
`QueueStore::insert`, `OutboxStore::put_record` must be durable when they return `Ok` (one
transaction each); `save_state` is called on every queue tick.

## 2. Core hooks (`caelum-core`)
| Hook | Wiring |
|---|---|
| Ground escalation (SR-015, F-GND-11) | `Notice::Ops(OpsEscalation)` from the escalator → `PathBPublisher::publish_escalation` (instance key as `ItemSigner`). Never conditional on the MDS. |
| Alarm state changes (ICD-VEH §6) | Every alarm create / state change / acknowledge / end → `OpsRecord::Alarm` through the same publisher. Map acknowledged and ended to `OpsAlarmState::{Acknowledged, Ended}`. |
| Crew and instance status (ICD-VEH OI-3 rate) | Periodic `OpsRecord::CrewStatus` per active crew member and `OpsRecord::InstanceStatus` (health from the supervisor / technical alarms; `mds_link` from `MdsConnector::health`). Rate: configuration, until OI-3 is agreed. |
| Medical record (F-GND-12/13) | For each item call `caelum_mds::routing::route(kind, policy, health)`: `PathA`/`HoldLocal` → `MdsConnector::enqueue`; `PathAPrime` → ground `DownlinkQueue::enqueue` on MEDICAL (FHIR bundle file via `caelum_ground::fhir::bundle`); `PathB` → the publisher (above); `NotSent` → keep locally. Refuse the configuration `HoldUntilReconnect` with MDS `NotConfigured` (the record would never leave). |
| Summaries (F-GND-14) | Summary window job → `MedicalSummary` per crew × parameter → ground queue, MEDICAL, ROUTINE. |
| MDS sync | A task calling `MdsConnector::tick(now, transport)` every poll interval; every `TickReport::inbound()` observation goes through **normal ingest validation and alarm evaluation** (SR-016); `technical_alarm` raises / clears `technical.mds_unreachable` (CR-011 table gets that row). |
| Ground queue | A task calling `DownlinkQueue::tick(now, budget, attachment_store)` each second; send `Outbound.packet` on the ground link (Yamcs link on the ground side, vehicle downlink onboard), then `delivered(id)`; ground CFDP PDUs → `receive_pdu`. |
| Uplink (F-GND-07) | CFDP `Received { name, data }` at `uplink/<kind>/<file>` with its `<file>.sig.toml` → `verify_uplink` → `UplinkLedger::apply` → the owner applies (ruleset reload, protocol library, model registry, config bundle); audit `uplink.apply` / `uplink.refuse`. Rollback via `UplinkLedger::rollback`, administrator + re-auth. |
| FHIR / research export (F-SYS-08) | `fhir::bundle` and `research::ResearchExporter` behind export commands; the research key is generated per export and kept by the operator (never stored with the export). |
| Configuration | Signed bundles `ground` (APID plan, path B endpoint, CFDP entities) and `contact-schedule` via `GroundConfig::load_signed` / `ContactSchedule::load_signed`; CFDP MIB timers (`CfdpConfig`) and MDS `ConnectorConfig` belong in the `ground` bundle in a follow-up (no defaults). |

| Command | Roles | Returns / does |
|---|---|---|

| `uplink_list`, `uplink_apply`, `uplink_rollback` | Administrator (apply/rollback after re-authentication); CMO and Flight Surgeon read | Ledger and outcome; audited |

| `export_research` | Flight Surgeon | De-identified CSV of consented crew; audited |
| `mds_status`, `mds_release_held` | BME (release after re-authentication); CMO read | Health, outbox counts by state, held items with reason |

## 4. Ground profile (F-GND-08)
In `ground` profile the app parses downlinked packets with `ParsedTm::parse`, decodes OPS
(`OpsRecord::decode`) and MEDICAL (`MedicalSummary::decode`) records, runs the receiving
`CfdpEntity` for files, and feeds Yamcs (`YamcsLink`) and the Open MCT gateway: `GET /history`
and a WebSocket emitting the JSON messages of `plugins/openmct/README.md` (`ops_alarm`,
`crew_status`, `instance_status`, OPS fields only), authenticated per CLAUDE.md rule 6.

## 5. Open MCT plugin
`plugins/openmct` is a standalone pnpm package (own lockfile) and is not in the root workspace.
Decide whether to add it to `pnpm-workspace.yaml` and `tools/ci check-all` (`pnpm -C
plugins/openmct typecheck && pnpm -C plugins/openmct test`). Its tests load jsdom in a hook
because jsdom start-up is slow on this machine (see its README).

## 6. CI jobs needed
1. **Yamcs**: container `yamcs/example-simulation` (or a minimal Yamcs 5.x instance) with the
   fragment from `caelum_ground::yamcs::instance_config(Udp, "mdb/caelum-ops.xml")` and the MDB
   from `xtce::generate(plan, version, XtceScope::Ops)` (and `Full` on a second instance); a test
   binary publishes every OPS record kind and a MEDICAL summary per parameter; the job queries the
   Yamcs REST API and asserts each parameter value decodes (F-GND-02/03 gate).
2. **HAPI FHIR**: container `hapiproject/hapi:v7` (R4); with the production transport, run the
   connector sync both ways and the unplug test (stop the container mid-run) — R-INT-06/07 gate.
3. **CFDP interop**: `cfdppy` (Python, `spacepackets-py`) as the ground entity receiving class 1
   and class 2 files from `CfdpEntity`, with a lossy UDP relay; plus a fuzz target for `cfdp::parse`.
4. **Open MCT**: build the plugin and load it into an Open MCT 4 app in a browser test against a
   fake gateway (crew board shows NO DATA, then a status).
