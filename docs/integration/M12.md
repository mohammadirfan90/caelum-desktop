# M12 integration: what the lead wires (F-ML-01..04, SR-002, CR-018)

`caelum-ml` is complete as a library: packages, verification, registry, feature builders,
time-limited runtime, ONNX Runtime backend (feature `onnx`), explanations, advisory notices and the
observe-only gate. Nothing outside `crates/caelum-ml` was changed. This file lists the wiring
that remains, in the paths the M12 library work could not touch.

## 1. Core hook (`caelum-core`)
- **State.** `Station` owns a `caelum_ml::registry::Registry` and, per crew member, a short
  history of numeric samples (`caelum_ml::features::Sample`) covering the longest `window_s` of
  any installed manifest (`Registry::manifest(id).features`). Store every numeric reading with its
  quality; the builder itself treats POOR/UNUSABLE readings as gaps (SR-005).
- **Startup.** For each package directory in the models directory (signed configuration, read
  only): `caelum_ml::package::load_dir(dir, &built_in_keys(), TrustPolicy::for_this_build())`.
  Refused packages are audited (`model.reject`, reason) and listed as DISABLED with the reason;
  verified ones go to `Registry::install(pkg, &factory)` and are audited (`model.install`, id,
  version, `manifest_sha256`). `factory` is `caelum_ml::onnx::OrtFactory::new(config)` in builds
  with `onnx`, else `caelum_ml::runtime::NoRuntime` (models then show UNAVAILABLE).
- **After observe** (`Station::observe`, after `self.alarms.observe(..)`): append the sample to
  the history; at each model's cadence (suggest: every 10 s per crew member, not per sample; run
  off the 4 Hz tick so the ingest path is never blocked by an inference: `evaluate` blocks for at
  most `time_limit_ms × (1 + features)`, so call it from a worker task, not the ingest thread)
  call `Registry::evaluate(id, crew, &history, now)`.
  - `Err(EvaluationError::NoData(_))` → model output shown as NO DATA for that crew member;
    `Unavailable`/`Disabled` → status only; `Runtime(TimedOut|Busy|WorkerLost|Run)`,
    `Implausible`, `OutputShape`, `Explanation` → no output, log and count (show "model error"
    after repeated failures). Never show a previous value as current.
  - `Ok(results)`: store each `AdvisoryResult` (derived observation, classification `Derived`,
    provenance: model id, version, manifest sha256; its `contributions` as the explanation).
  - For each result with `parameter` set (M2 → `af_probability`):
    `ObserveOnlyInput::new(&res, None)?.apply(engine)` and persist the returned events through the
    existing `AlarmService::persist` path. This needs a small `AlarmService` method that lends
    `&mut Engine` to the gate (e.g. `fn apply_model(&mut self, db, input: ObserveOnlyInput)`);
    `apply` re-checks admissibility against the engine's own ruleset. A `GateRefusal` is logged
    and audited, never retried with another parameter.
  - For each result: `AdvisoryNotice::from_result(&res)` → an observe-level notice (priority
    `level().priority()` = observe, observe escalation plan only), shown with title, action,
    model id, validation status and explanation. Do not also notify for outputs that feed
    `af.observe` (M2 manifests should carry `parameter` and no `notice`).
- **SR-002.** Never pass a model result to `Engine::evaluate`, `acknowledge`, silence, escalation or
  the technical monitor directly. The gate is the only entry. Add a core-level test feeding the
  M12 adversarial runtimes through the station path if the hook adds logic.

## 2. IPC and UI ("validation status shown in UI", F-ML-01, F-ML-04)
- `model_list` (read; roles per ROLE_MATRIX: clinical roles and the astronaut for own data; never
  MCC/OPS: physiology): `Registry::statuses()` → `ModelStatusView` (id, name, version,
  validation, status `VALIDATED | INVESTIGATIONAL | DISABLED | UNAVAILABLE`, reason,
  development_signed, gate, intended_use, limitations, model_sha256).
- `model_disable` / `model_enable` (CMO or administrator, re-authentication, audited).
- Model results and notices in the crew-member view: value, label, time, quality, status badge
  (text, not colour only: "ADVISORY · INVESTIGATIONAL"), and the top contributing features
  (feature, value, reference, delta). Development-signed packages show a DEVELOPMENT MODEL badge.
- Generate bindings with `tauri-specta` as for every command; add the commands to ROLE_MATRIX.

## 3. Configuration
- Application configuration gains `[ml] onnxruntime_library = "<path>"`,
  `onnxruntime_sha256 = "<hex>"`, `intra_threads = 1`, `models_dir = "<path>"`, mapped to
  `caelum_ml::onnx::OrtConfig`. Default: the library shipped next to the executable
  (`onnxruntime.dll` / `libonnxruntime.so.1.x`) with the pinned checksum compiled into the release
  configuration. Missing or mismatching → UNAVAILABLE (no fallback).
- `src-tauri`: enable `caelum-ml/onnx` in development and release builds once §4 and §5 are done;
  bundle the library as a resource (`tauri.conf.json` `bundle.resources`).

## 4. Tool cache and offline build
- Add the pinned ONNX Runtime CPU binaries (Windows x64 `onnxruntime.dll`, Linux x64
  `libonnxruntime.so.1.x`; version ≥ 1.22, matching `ort` 2.0.0-rc.13's API floor `api-22`) to the
  tool cache under `onnxruntime/` with source URL, version, fetch date, licence (MIT) and
  SHA-256 in `MANIFEST.sha256` (`docs/OFFLINE_BUILD.md` §1–2); `tools/offline/verify.ts` and
  `build-offline.ts` copy it into the bundle and write its checksum into the release config.
- The SBOM must list the ONNX Runtime binary as a component.

## 5. Supply chain and SOUP register
- `deny.toml`: `libloading` (ISC) is pulled in by `ort` `load-dynamic`; add `ISC` to the allow-list
  or an exception for `libloading` before enabling `onnx` in a checked graph (`[graph]` checks
  default features today, so CI passes now).
- `docs/third-party-risk.md` rows (move the "Known risks" `ort` bullet into the table):
  - `ort`, `ort-sys` `=2.0.0-rc.13`, default features off, `load-dynamic` + `api-22`: ONNX
    inference (F-ML-01). Risk: release candidate, API drift; native library loaded at run time.
    Mitigation: exact pin, used only in `caelum_ml::onnx`; library checksum verified before load;
    hard time limits; outputs range-checked; outputs advisory only (SR-002). M12.
  - ONNX Runtime binary (pinned, tool cache): Risk: native code, numerical bugs, slow kernels.
    Mitigation: checksum, CPU only, fixed threads, time limit, range checks, SR-002 gate. M12.
  - `libloading` 0.9 (ISC, via `ort`): dynamic loading. Mitigation: only the checksummed library
    path is loaded. M12.
